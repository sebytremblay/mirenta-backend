# Mirenta Backend MVP: Decision Record

This file records the current system-design decisions for the backend MVP. Each entry states the decision as it stands today. Where a later finding overturned an earlier choice, the entry reflects the current answer and names the rejected alternative in place, so a reader who lands on a single decision reads the current truth rather than a superseded one. One entry, D45, records an alternative the team considered and rejected; it states why the premise failed and points to the decision that replaced it, so code that cites it resolves to an accurate account.

The detailed designs that implement these decisions live in [mvp-pipeline-architecture](mirenta-docs/technical/mvp-pipeline-architecture.md), [mvp-data-model](mirenta-docs/technical/mvp-data-model.md), and [research-agent-design](mirenta-docs/technical/research-agent-design.md). Deferred work and the items that remain open live in [BACKLOG](mirenta-docs/technical/BACKLOG.md).

## Framing

Three framing answers shape every decision below:

- **Backend only.** This program builds the backend API. A co-founder owns the frontend, onboarding UI, campaigns, email, and go-to-market. Decisions that belong to those tracks fall out of scope.
- **Fresh standalone backend.** The earlier `mirenta-website` repository held an unrelated competitor-ads prototype a co-founder added as reference. The founder discarded it and deleted the repository. No code carries forward.
- **External multi-tenant SaaS, Salesforce-first.** Mirenta sells to SDRs and founders who self-serve and pay. The MVP proves the Salesforce HR and ITSM vertical, on a research schema that stays vertical-agnostic underneath.

| D43 | Public-page disclaimer | No disclaimer. The page ships without an AI-generated or unaffiliated notice, which preserves the authentic effect and carries the accepted content and affiliation exposure. |
| D44 | Public API surface for a seller-triggered regenerate | A `regenerate: true` flag on `POST /leads` that references the existing `lead_id`. The response reuses the D15 `leadId` to `jobId` map, so a regenerate adds one map entry keyed on the referenced `lead_id`. |
| D45 | Agent runtime, in-process loop (considered and rejected) | Rejected. An earlier session concluded the backend must run the agent loop in-process because the `ANTHROPIC_API_KEY` appeared to 401 against the Managed Agents endpoints. A direct probe disproved the premise: the 401 came from the dev shell exporting `ANTHROPIC_BASE_URL` (a Salesforce browser-auth gateway) plus `ANTHROPIC_AUTH_TOKEN`, which the SDK inherits from the ambient environment, not from the key. The key is a genuine first-party Anthropic key and Managed Agents is reachable, so the Research Agent runs server-side instead (D13, D50). The config pins the host through `MIRENTA_ANTHROPIC_BASE_URL` and ignores the ambient `ANTHROPIC_BASE_URL`, so the gateway cannot leak in. |
| D46 | Worker host for the MVP | A standalone Node worker hosts the MVP tick. It creates the research Managed Agents session, holds it open synchronously within one tick, collects the result, and runs the one-shot build in the same tick. Anthropic holds the research loop (D50), so the worker carries no heavy loop itself; it stays open only to hold the session synchronously. The Supabase scheduled-plus-edge-function host (D32) and the webhook-driven short-tick split reopen as a fast-follow. |
| D47 | Model pinning during the build | Every agent call pins to `claude-haiku-4-5-20251001` for the prove-out phase, at the founder's explicit instruction, to avoid burning tokens before the system runs end to end. Models read from `ANTHROPIC_RESEARCH_MODEL` and `ANTHROPIC_BUILDER_MODEL`. The research model bakes onto the persistent Managed Agents agent at provisioning time, so restoring it needs an env edit plus a re-run of `scripts/provision-managed-agents.ts`; the builder model reads at runtime and takes effect on the next build. Restoring the D35 tiers is therefore config plus a re-provision for research, config alone for the builder, never a code change. |
| D48 | Brand assets for the MVP page | The Website Builder renders each page in the prospect company's own visual identity. The Research Agent extracts the prospect brand tokens (brand colors, primary font, and absolute https URLs for the logo and favicon) during a dedicated brand-capture phase and emits them on the research object; the builder maps them onto a per-lead CSS custom-property block, falls back token by token to the seller-supplied brand and then to house defaults, and prefers the prospect logo and favicon over the seller logo. Sourcing the tokens inside the research session keeps fetch-and-inline off the builder hot path. The page stays one self-contained HTML file with no per-lead build step. The logo and favicon load by URL; inlining them as data URIs for full self-containment stays a hardening fast-follow in [BACKLOG](mirenta-docs/technical/BACKLOG.md). |
| D49 | ROI model fidelity for the MVP | The ROI model applies the fixed per-employee ticket and interaction volumes from the workflow reference (10 IT, 8 HR) to total headcount and presents net annual savings across conservative, expected, and aggressive scenarios, which satisfies the D38 shape the page renders. The value model now also computes the payback period, the 8% NPV, and the five-year cumulative projection (under an adoption ramp), surfaced as metric tiles and an SVG chart on the page; these previously deferred pieces ship. The model still does not implement the full Step 4 tiered cost mix and named per-tier deflection rates; those remain in [BACKLOG](mirenta-docs/technical/BACKLOG.md), and the headline figure stays a defensible blended estimate. The extension stays vertical-neutral: the value model returns generic `metrics` and a `projection` the page renders without a vertical branch. The `it_staff` and `hr_staff` counts persist in the research object for the fuller model. |
| D50 | Agent runtime | The Research Agent runs as a Claude Managed Agents session: Anthropic holds the loop server-side, the agent searches through Exa's hosted MCP server (authenticated by a vaulted `static_bearer` credential keyed to the MCP URL, with the toolset set `always_allow`), and the worker harvests the final research object from a custom `emit_research` tool. The Website Builder stays a one-shot Messages API call (`generateStructured` with a forced `tool_choice`), since a single structured generation has no multi-step loop for Managed Agents to host. The worker drives the research session synchronously within one tick for the MVP (D46); the webhook-driven start, poll, collect split reopens with D32. The config pins the API host through `MIRENTA_ANTHROPIC_BASE_URL` (default `https://api.anthropic.com`) and deliberately ignores the ambient `ANTHROPIC_BASE_URL`, so the dev-shell gateway that misled the rejected D45 cannot leak in. |
| D53 | Vertical coverage of the research agent | One generic persistent research agent serves every vertical. The system prompt stays vertical-neutral and byte-stable, so Anthropic caches the prefix; the per-lead kickoff carries the vertical brief (domains, executive targeting, value-input guidance), which varies and caches nothing. The active vertical enforces its required value-input keys in code, while the frozen `emit_research` tool schema keeps `value_inputs` a permissive open numeric map. |
| D54 | Page-generation trust boundary | The model authors the whole document (D9), so a deterministic validator at the page boundary, not the model, holds the load-bearing invariants: the document parses complete, it renders every precomputed value figure verbatim, it carries no unsafe construct (no script, iframe, object, embed, form, inline event handler, or `javascript:` URI), it references only allow-listed external hosts (Google Fonts plus the resolved logo, favicon, prospect, and booking hosts), it surfaces no unverified quote, and it exposes the required section anchors and hero banner. The MVP rejects a noncompliant page rather than sanitizing it, which keeps the boundary simple; an HTML sanitizer reopens as a fast-follow if reject rates run high. A violation throws a typed error the builder retries with a corrective note up to a bound, then fails. A truncated document classifies transient (the worker retries it on the lease); a clean contract violation classifies permanent (the job fails loudly rather than publishing a broken page). The builder, not the model, welds in the one approved count-up script and a defense-in-depth meta CSP after validation passes, so no model-authored JavaScript ever ships and S3 still serves a page with a content-security policy (S3 sets no headers, D16). This validator does not relax D31 (no prompt-injection guardrails) or D42 and D43 (the page still reproduces the prospect identity with no disclaimer, accepted risk); it bounds output safety and contract conformance, not the accepted content exposures. |
| D55 | Per-lead token-usage telemetry | The worker records token usage per agent stage in a new `token_usage` table (migration 0005), the precursor metric the deferred spend ceiling (D33) lacks. It writes one row per stage per job, one `research` and one `builder`, so the per-lead total sums the job's rows and the research-vs-builder breakdown reads off the `agent` column. Each row carries the raw input, output, cache-write, and cache-read counts for granularity, a request count, the billing model, and a `cost_usd` computed at write time from a per-model rate table (`src/providers/pricing.ts`) so a later price change never rewrites history. The research path accumulates usage across the Managed Agents `span.model_request_end` events; the builder reads it off the Messages `response.usage` and sums it across corrective retries, so the totals count real spend honestly rather than deduping retries away. The worker records the spend right after the agent returns, before the guarded transition, since the tokens are spent whether or not the transition wins its race. Telemetry writes are best-effort: a usage-write failure logs and returns rather than failing a job whose real work already succeeded. Tenancy keys on `org_id` in application code (D30). The cost rates assume the default 5-minute cache TTL (D8); the Sonnet, Opus, and Fable rates ride along for the D35 tier restoration, and an unpriced model records a zero cost rather than guessing. |

## Notable rationale

A few decisions carry consequences worth stating plainly.

**D15 reshaped the API contract.** The batch-submit model returns a map of `leadId` to `jobId`, and the client polls each job independently. A nullable `batch_id` groups jobs for rollup status without pulling campaign lifecycle into the backend.

**D17 and D18 set tenancy at the org.** The SaaS decision (D3) makes organization tenancy the right foundation, and Supabase Auth supplies the session that mints identity server-side. The client never asserts the tenant.

**D34 and D40 split deduplication across two layers.** The frontend dedupes leads on upload (D40), so the backend adds no uniqueness constraint to the `leads` table. The Lead Service still dedupes at submission on `org_id` plus email (D34) to stop a double-submit from spending twice, and a regenerate flag bypasses that dedupe to force a fresh job when a seller chooses to rebuild a page (D44).

**D50 enforces quote rigor through the prompt, with a backstop.** Under Managed Agents the agent calls Exa's hosted MCP directly, so no code-level re-fetch hook exists. Verification rigor rests on the agent's system prompt, which instructs it to re-fetch each source and drop any quote that fails (D37). The Website Builder's verified-only filter remains as a backstop. The strict-enforcement variant, which services Exa as a custom client-side tool over SSE and preserves a `VERIFICATION_FAILED` injection point, stays available if prompt-level rigor proves insufficient.

**The MVP carries accepted risk, concentrated on the public page.** The MVP ships without RLS (D30), without prompt-injection guardrails (D31), without a spend ceiling (D33), without a research-quality gate (D36), and without a privacy lawful-basis or erasure path (D41). The public page compounds this: it reproduces the prospect's full visual identity (D42, D48) under the seller's outbound brand with no disclaimer (D43). A deterministic validator now rejects an unsafe or noncompliant page (D54), which bounds output safety, but it neither sanitizes nor relaxes the content-exposure risk those decisions accept. Each item is logged in [BACKLOG](mirenta-docs/technical/BACKLOG.md) with its trigger. These are real exposures the team accepts to prove demand, and they should reconcile before meaningful external traffic.

**D55 gives the deferred spend ceiling its baseline.** D33 defers a spend ceiling and a rate-limit circuit breaker to BACKLOG, which leaves the MVP with no measured cost per lead to optimize against. The `token_usage` table closes that gap without taking on the deferred work: it observes and attributes cost, it does not cap it. Storing the computed `cost_usd` at write time, keyed to the billing model, means the baseline survives both the D35 tier restoration and any later price change, so the numbers a future spend ceiling sets stay grounded in real history.

**Verify a load-bearing claim before the architecture turns on it.** The rejected D45 rested on a premise that one failed call seemed to confirm: that Managed Agents was unreachable. A direct probe against the real API disproved it; the 401 came from the dev shell's inherited `ANTHROPIC_BASE_URL`, not the key. The config now pins `MIRENTA_ANTHROPIC_BASE_URL` and ignores the ambient gateway so the failure cannot recur. The lesson holds beyond this case: probe the real interface before concluding a feature does not exist.
