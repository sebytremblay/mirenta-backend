GENERIC CORE, A FAMILY OF SEAM GAPS

The system's broad structure is well generalized: the vertical (a data-only registry) and the deployment and provider knobs (env-overridable config) sit cleanly behind seams that settled D-decisions sanction. But a targeted second pass found six places where a constant feeds a customer-facing value yet bypasses an existing per-customer or per-vertical seam built to hold its siblings. Two are high severity, both inside the ROI math. This is a recurring pattern, not one stray literal.

Why this section grew. The first automated pass graded every value-model constant "acceptable," leaning on D49's language that the ticket and interaction volumes are fixed. That over-reached: D49 fixes the volumes for the MVP model fidelity, not as a statement that the economics are customer-invariant. A skeptic told to default to "acceptable" rationalized real gaps against an adjacent decision. A second workflow inverted the bias, hunting specifically for constants that bypass an existing seam, and surfaced the family below. Per the founder's direction the code stays as-is; this report records the gaps honestly so the decision is explicit, not implicit.

What is already well generalized

The audit credits the seams that hold the product's real variation.

  • Vertical registry is genuinely data-only. src/verticals/index.ts resolves any spec by id and DEFAULT_VERTICAL_ID derives from the spec rather than repeating a literal. Adding a vertical is a registry add with no core edit (D2, D20).
  • Per-customer economics are lifted out of constants. VerticalEconomics reads from profile.economics through a factory with a defaultEconomics() fallback (migration 0007, D57), so two customers share one vertical with different numbers.
  • Provider and deployment knobs are env-overridable config. Model ids, base URLs, the S3 bucket and region, and the worker lease, batch, poll, and attempts bounds all flow through optional() and intOptional() in src/config/env.ts (D47, D35, D50, D16).
  • Brand theming follows the D48 precedence chain (prospect → seller → vertical → house), each token falling back independently, with HOUSE_NEUTRAL as a documented backstop rather than a buried magic value.
  • Status strings and usage labels are compile-time unions. JobStatus and TokenUsageAgent make the literals type-checked members, so a typo fails the build.
  • Multi-tenancy resolves server-side. The gateway derives org_id from a verified Supabase session, never from the path or a client assertion, so the route table is tenant-invariant by design.
  • The host security boundary is an intentional fixed allow-list. Always-allowed hosts and the CSP are coordinated and enforced independently of theming (D54). The font allow-list rides on this boundary but doubles as a closed curation table; finding 6 below treats that curation, not the host check, as the gap.
  • Disclosure policy is centralized. A single DISCLOSURE_SCENARIO_NAMES constant feeds both the save-time economics gate and the build-time render gate, so the two enforcement points cannot drift (D38, D49, D57).

The seam-asymmetry family

One shape repeats: a constant feeds a customer-facing computed or rendered value, the value varies by customer / vertical / region, yet the constant sits outside the seam (VerticalEconomics, VerticalSpec, ProductProfile.brand) that already holds its siblings. None blocks the build today; each lets a value render that a customer cannot correct. Ordered by severity.

1 · Per-contact cost basis bypasses per-customer economics high

The ROI figure is employees × volume × cost-per-contact × deflection. D57 lifted pricing, effectiveness, and the adoption curve into VerticalEconomics, but the per-contact cost, the largest single dollar lever, stayed a module constant. A customer sets their license price and deflection rates yet cannot touch the cost their savings derive from. D49 sanctions the cost as a "defensible blended estimate," not as customer-invariant.

Bypassed seam: VerticalEconomics (D57). Inline 1.08 NPV discount rate (line 219) has the same shape: cost of capital is customer-specific.

src/verticals/employee-service.ts:30-31 — IT_BLENDED_COST_PER_TICKET=22, HR_BLENDED_COST_PER_INTERACTION=18
src/verticals/employee-service.ts:163-164 — createCompute multiplies them into itAnnualCost / hrAnnualCost
Fix: add the cost basis (and the discount rate) to VerticalEconomics, with defaultEconomics() supplying today's 22 / 18 / 0.08 as the fallback.

2 · Per-employee contact volumes bypass the same seam high

The cost basis's own multiplicative co-factor, on the line directly above it. IT_TICKETS_PER_EMPLOYEE_YEAR=10 and HR_INTERACTIONS_PER_EMPLOYEE_YEAR=8 propagate through the identical ROI chain: every scenario gross/net/ROI, the headline, payback, the five-year cumulative, the rendered projection, and the NPV. A regulated bank or a field-heavy manufacturer generates a different ticket rate than a software firm, yet a customer can override price and effectiveness but not volume. Same severity as the cost basis because it rides the same chain.

Bypassed seam: VerticalEconomics (D57). D49 fixes the volumes for MVP fidelity, which is not the same as declaring them customer-invariant.

src/verticals/employee-service.ts:24-25 — the two volume constants, labeled only "Reference assumptions from the workflow doc"
Fix: add it_tickets_per_employee_year / hr_interactions_per_employee_year to VerticalEconomics, validate them in validateEconomics, read through createValueModel with the current values as defaults.

3 · "5-year net savings" label hardcodes a horizon the adoption curve can contradict medium

The cumulative figure correctly sums over however many years the adoption_curve supplies, and validateEconomics imposes no five-element constraint. But the metric tile always reads "5-year net savings." A customer who sets a 3- or 7-year curve via profile.economics gets a tile labeled "5-year" showing a different horizon's number, on a trust-sensitive prospect-facing ROI tile. The math is right; the label lies.

Bypassed seam: VerticalEconomics.adoption_curve (the data is dynamic, the label is static).

src/verticals/employee-service.ts:229 — literal "5-year net savings" label against the dynamic cumulative5 series
Fix: derive the horizon from the curve length, e.g. `${adoption.length}-year net savings`, so the claim always matches the summed series.

4 · Surface palette neutrals bypass the brand seam the accent uses medium

The primary color resolves through the full D48 chain (prospect → seller → vertical → house). Its companion neutrals do not: bg and text fall from a prospect override straight to a module literal with no seller or vertical tier, and surface, surfaceMuted, muted, border, radius have no override path at all. A vertical or brand with a dark or high-contrast identity renders its accent through the seam while the neutrals stay light-gray, a palette mismatch on the page. Medium because bg/text keep a prospect override and no money figure is touched.

Bypassed seam: VerticalSpec.defaultAccentColor already proves the spec can hold render tokens (D20); only the accent uses it.

src/agents/brand-tokens.ts:141-162 — surface neutrals as module literals, only primary routes through the fallback chain
Fix: extend VerticalSpec (and optionally profile.brand) with the surface neutrals so they resolve through the same tiered fallback, keeping today's literals as the house default.

5 · formatDollars ignores the per-result currency unit that already exists medium

formatDollars hardcodes the $ glyph, the K/M suffixes, and toLocaleString("en-US"), and feeds every customer-facing dollar string. Meanwhile ValueProjection.unit already declares the series currency ("USD") and the renderer ignores it. An EU prospect should see euro grouping and EUR. This is the same single-currency posture the low-severity theme below describes, but graded medium here because a partial seam (unit) already exists and is bypassed, rather than absent.

Bypassed seam: ValueProjection.unit (declared per-vertical, unused by the formatter).

src/domain/format.ts:6-12 — $ glyph, K/M suffixes, en-US locale
src/verticals/types.ts:65 — ValueProjection.unit set to "USD" but never threaded into formatDollars
Fix: thread the unit into formatDollars (deriving symbol and locale) and propagate it to the headline, scenario, and metric sites that lack it. Larger than the others; pair with the currency theme below.

6 · Google Fonts allow-list is a closed table a customer brand cannot extend low

A brand whose typeface is absent from the 20-entry table silently wears the system stack instead of its own face. The renderable-font set varies by customer brand and a seam already exists (profile.brand carries the sibling color and logo tokens). The security objection does not sink it: the host boundary is enforced independently by the validator's allow-listed hosts and CSP (D54), so a per-customer extension can still supply structured, validated font records. Low because the failure mode is graceful degradation to a readable font, not a wrong figure or broken page.

Bypassed seam: ProductProfile.brand (holds primary_color and logo_url already).

src/agents/brand-tokens.ts:31-52 — GOOGLE_FONT_ALLOW_LIST as a frozen module table
Fix: allow validated per-customer font records via profile.brand or deployment config, keeping the 20 current entries as baseline.

Correctly excluded

The skeptic rejected three candidates that look similar but are not seam asymmetries. Recording them so the line stays clear.

  • Footer disclaimer copy (builder-prompt.ts:193) is a single product-level decision (D43, reaffirmed D54), not a stranded sibling. Letting the seller edit Mirenta's own liability notice would defeat its purpose.
  • Per-model USD rate table (pricing.ts:25-33) is the vendor-fixed Anthropic price list, identical across every deployment, and it feeds internal telemetry (cost_usd), never a customer-facing figure (D33, D55).
  • Cache-write multiplier 1.25 (pricing.ts:22) feeds the same internal telemetry and is sanctioned by D8/D55 for the 5-minute TTL. The 1-hour-TTL undercount is hypothetical future coupling, not a present gap.

Residual themes (low severity)

Every item below resolved to acceptable or low. None blocks a second vertical, customer, model, or region. They are hygiene, not coupling defects.

USD / en-US is a system-wide posture, not just one formatter low

Finding 5 above names the bypassed unit seam at formatDollars. Stepping back, the single-currency assumption runs end to end: the economics fields are documented USD, no currency or locale field exists upstream on any profile or research input, and no decision scopes a non-US region. So the proper fix is not to patch one formatter but to introduce a currency/locale abstraction across the formatter, the economics shape, and the verbatim-figure validation gate together, as one scoped change. The honest formatDollars name makes the contract and the future migration explicit.

src/verticals/types.ts:102-103 — economics fields documented as USD with no currency field to thread
Recommendation: treat finding 5 as the entry point but defer the full multi-layer change until a non-USD customer is actually scoped, raised as a new open decision. Extracting one literal in isolation would be incoherent.

Operator-brand and copy literals are single-deployment defaults low

The Mirenta operator name appears as literals in the builder brief and the footer, and copy defaults like the CTA fallback are fixed English. These are correct for a single-operator product: every dimension that actually varies (seller, lead, lead company, vertical, brand) is already parameterized, and Mirenta is the one fixed top-of-chain party. No decision sanctions white-labeling; D3 multi-tenancy means many sellers on one Mirenta-operated platform.

src/agents/builder-prompt.ts:57, 63, 193 — "Mirenta" in the system brief, animation line, and footer
src/agents/builder-prompt.ts:202 — CTA fallback for the empty optional cta_text
Recommendation: keep the operator literals; lift them to config only if white-label enters scope. One real wart worth fixing: the footer claims figures "model industry benchmarks" unconditionally, mildly inaccurate on non-estimated runs. Make that claim conditional on inputs.estimated.

Duplicated-constant and stale-default hygiene nits low

A handful of constants are duplicated or stale enough to drift, though each is bounded by a loud-failure guard, a type check, or being unreachable. The clearest cases are an active-job status array re-listed inline, a dead max_tokens fallback that diverges from config, a duplicated AI-filler denylist, and index.html written twice. (The inline 8% discount rate, first listed here, is promoted into the cost-basis gap above, since cost of capital is also customer-specific.)

src/db/client.ts:154 — active-job status set inlined instead of derived from JobStatus (a new in-flight status forgotten here drops silently from dedupe)
src/providers/anthropic.ts:61 — max_tokens fallback 8000 diverges from config 16000; dead today but misleading
src/agents/builder-prompt.ts:100 & src/agents/research.ts:93 — the same six filler words duplicated with order drift
src/providers/storage.ts:18-20, 46 — "index.html" literal written twice
Recommendation: optional opportunistic cleanup. Highest value: express the dedupe status set as "all statuses minus failed" so the intent is explicit, and drop the stale 8000 fallback by making maxTokens required. Do not couple the two byte-stable prompt prefixes to dedupe the filler list, since that would bust the prompt cache (D8, D50).
